# 実行可能な仕様を中心にした開発手法

新規プロジェクトで、開発者とAIが同じテストから観測可能な仕様を読める状態を作る。言語やテストランナーを固定しない。既存プロジェクトの全面移行は対象外とする。既に本手法を採用したプロジェクトでの変更、バグ修正、リファクタリングには継続して使う。

## 情報の置き場所

| 情報 | 正本 | テストからの取得方法 |
|---|---|---|
| 利用者、業務目的、用語、責任範囲 | 既存のRequirement・業務コンテキスト | 機能単位の参照 |
| 入力、結果、状態遷移、エラー、禁止する副作用 | 通常のテストに書いた受入条件 | 仕様IDとテスト本体 |
| テストだけでは表現できない受入条件 | Specの該当項目 | 同じ仕様IDに検証義務を接続 |
| 設計判断の理由と適用範囲 | 現在有効なADR | 対象の制約から参照 |
| 変更する範囲 | Work Packageまたは現在のタスク | 上流参照 |
| 必要な検証と今回の結果 | 既存のVerification・Evidence | 仕様項目への参照 |
| 探すための一覧 | 生成した仕様索引 | 正本の場所と鮮度を確認 |

テストだけで業務判断の理由や運用環境まで推測させない。テストを入口に、必要な根拠へ短く到達させる。既存の`docs/lifecycle-artifact-contract.md`の責任分担を保ち、同じ文章を各成果物に複製しない。

## 初回セットアップ

1. リポジトリ、使用言語、テストランナー、CI、既存の配置規約を確認する。新規プロジェクトでも未決定の業務ルールをAIが確定しない。技術選択は実際に必要になるまで保留できる。
2. [テンプレート](project-templates.md)を使い、`docs/ai/executable-spec-profile.md`を作る。言語、正本の場所、テスト探索方法、索引の更新・検査コマンド、通常検証、広域検証、実行条件をリポジトリの事実から記入する。未実装のコマンドは`unavailable`とし、利用可能だと報告しない。
3. 代表的な一機能に、目的・利用者・用語・境界を置く。既存のRequirement等があれば参照だけにする。テストは既存のfeature/core/shared等の配置に従い、仕様専用の並行ディレクトリへ一律に移動しない。
4. [記述規約](spec-writing-conventions.md)に従い、通常のテストへ安定した仕様項目IDを付ける。正常系、境界、拒否時の結果と副作用を含め、必要なら状態遷移・不変条件を追加する。確認できていない判断は`provisional`のまま残す。
5. [仕様索引](spec-index.md)の最小形式で、テストと非ユニット検証の入口を結ぶ。採用先のランナーや既存メタデータから決定的に生成する小さなアダプターを選ぶ。適合するものがなければ、そのプロジェクトの言語・記法に限って作る。全言語を解析する独自フレームワークは作らない。
6. [情報取得手順](context-retrieval.md)と[検証範囲](verification-selection.md)をプロジェクトルールから参照する。既存の`AGENTS.project.md`等へ短い入口を追加し、規約本文をコピーしない。
7. 仕様追加、バグ修正、振る舞いを維持するリファクタリングの代表タスクで、必要な仕様へ到達できるか、変更対象外の条件を維持できるか、検証範囲を説明できるかを確認する。サンプルの成功を実プロジェクト全体の有効性とみなさない。

登録する本スキルは規約・参照・テンプレートを提供する。採用先の索引生成コマンドやCIは、採用先で実装・実行するまで未設定である。スキルの登録完了と、個別プロジェクトのセットアップ完了を分ける。

## 開発時の手順

1. 変更要求を既存の仕様項目または追加する受入条件に結び、情報取得手順で読む範囲を決める。
2. 変える仕様、維持する仕様、未決事項を分ける。既存Specがある場合はIDを再利用し、必要な差分だけを記録する。
3. `test-first-verification`で既存のproof policyに従う検証を定める。振る舞いを示す失敗を先に観測できる場合は記録する。構文エラー、未実行、ランナーの失敗を期待した失敗と混同しない。
4. 最小限の実装で満たし、選定した検証を実行する。新たな影響が見つかったら読む範囲と検証範囲をそれぞれ更新する。
5. 振る舞いを維持して構造を整理する。業務・互換性の期待値を維持し、設計に依存するテストの変更理由を明示する。
6. 索引を再生成し、参照切れ・受入条件の検証漏れ・未実行の義務を確認する。完了報告は既存のImplementation Contractから証拠を参照する。

テスト追加と実装を同じAIが行う場合も、期待値の根拠は要求・合意済みの条件に求める。実装の結果をそのまま期待値に写さない。重要な条件は境界例、反例、性質ベースの検証や別の観点からのレビューで確かめる。

人が仕様を動きで確認したい場合は、[シナリオによる確認](scenario-visual-review.md)を追加できる。実装前は受入条件のプレビュー、レビュー時は保持した仕様・テストの期待・実測の比較として使う。既存の仕様IDとproof policyを引き継ぎ、独立した仕様正本や必須の動画生成工程を作らない。

## 小さく維持する

- 既存のテストランナー、assert、fixtureを使う。独自の期待値記法を必須にしない。
- メタデータは探索・権威・変更寿命に必要なものに限る。実装ファイルの全一覧や網羅的な依存グラフを手で維持しない。
- 重複するテストは、守る条件を残した上で統合する。バグの再現条件を削除する場合は代替となる検証を示す。
- アーキテクチャ変更時はADRと設計依存テストを再評価する。業務仕様のIDと観測可能な結果を維持できるかを先に確認する。
- 保守負荷が増えたら、重複メタデータ、不要な実装詳細へのassert、巨大fixture、古い参照から見直す。テスト本数や行カバレッジだけを成功指標にしない。
