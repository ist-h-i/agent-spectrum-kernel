# 検証範囲の選定ルール

この参照は必要な検証を選ぶ補助である。検証の表現と完了条件は`test-first-verification`と`ask.verification-proof-policy@1.0.0`が決める。独自のproof区分、免除、完了判定は作らない。

## 選定に使う入力

変更する仕様項目、維持する条件、実際のdiff、ソース依存、共有する業務ルール、API・イベント・保存形式の利用関係、設定・DI等の実行時接続を使う。コードの依存グラフだけから影響がないと結論しない。

| 変更の性質 | 少なくとも候補に含める検証 | 広げる条件 |
|---|---|---|
| 局所的な業務ルール | 当該条件、境界、拒否時の副作用、不変条件 | 同じルールを使う機能がある |
| バグ修正 | 修正前の再現、修正後の回帰、同種の境界例 | 根因が共有コード・設定にある |
| 内部構造だけの変更 | 既存の業務・互換性テスト、必要な静的検査 | 責任・依存方向・公開契約が動く |
| core/shared、fixture、ビルド・テスト設定 | 影響する利用側、型・ビルド、テスト探索の確認 | 利用側や動的接続を特定できない |
| API、イベント、保存形式 | 提供側・利用側の契約、結合、互換性 | 複数バージョン、外部利用者、移行がある |
| DB、外部I/O、並行処理、再試行 | 実環境に近い結合、失敗・競合・回復 | fakeが保証していない特性へ影響する |
| アーキテクチャ変更 | 維持する業務仕様、現行ADRの静的・境界検証、連携 | 機能間の責任やデータの所有者が変わる |
| UI・操作フロー | 関連ロジック、結合・操作、必要な実画面確認 | 状態、非同期、アクセシビリティ、視覚的判断が関わる |
| 性能・安全性・信頼性の主張 | その主張に対応する測定・専門検証 | ユニットテストで主張を支えられない |

表は適用条件を選ぶために使う。すべての行の検証を毎回必須にしない。仕様の網羅性は、要求から受入条件への対応でも確認する。

## 選定の手順

1. 変更対象を直接証明する最小のチェックを選び、バグなら可能な範囲で修正前の失敗を確認する。
2. 維持すべき条件と、境界を通じて影響する利用側のチェックを加える。
3. 高速で決定的なユニット群は、費用が小さければモジュール単位または全体を実行する。細かい選別の保守費用が実行費用を上回る仕組みを作らない。
4. 費用の大きい結合・E2E・測定は、仕様と境界の関係から選ぶ。除外する場合は対象条件と今回無影響と判断した根拠を示す。
5. 実装後のdiffを再確認する。予定外の設定・依存・生成物・公開面の変更があれば選定を更新する。
6. 既存のCI・merge・release必須検証を満たす。作業中のfocused checkで代替しない。規定された全体検証がある場合は維持する。

## 不確かな場合

- 索引や依存グラフが不完全なら、該当モジュールから関連機能群へ、さらに共有境界へと検証を広げる。根拠なく狭い選定を確定しない。
- 影響が広く特定できない場合は、利用可能な広域検証を選ぶ。実行環境・時間等で実施できない検証は未実施として残し、その義務に依存する完了主張をしない。
- flakyは成功扱いにしない。再実行結果と原因の不明点を区別し、隔離には根拠、担当、見直す条件、代替の証拠を持たせる。
- skip、収集件数ゼロ、selector不一致、古いrevisionの結果は、その仕様を検証した証拠にしない。
- mutation testingは重要な判断ロジックのテスト感度を調べる場合に選ぶ。全変更の必須処理や、仕様の完全性の証明にはしない。

## 結果の記録

既存のVerification Contractには、仕様項目、選んだチェックと理由、広げる条件、必要な証拠だけを置く。実行結果は、対象revision、コマンド、環境、実際の結果、未実施項目をEvidenceへ記録する。

リファクタリングで設計依存テストを置換した場合は、何の制約を廃止し、どの業務・互換性の証拠を維持したかを残す。テスト本数が同じことやgreenであることだけでは、過去の仕様を守った証明にならない。
