# シナリオを動かして仕様を確認する

既存のSpec・テスト・実行結果を、同じ場面の3つの見方として表示する。明示的な依頼または採用先の設定がある場合だけ使う。人が行動と結果を理解するための補助であり、既存のテスト、proof policy、レビューゲートを置き換えない。

## 情報の責任

| 見方 | 入力となる正本・証拠 | 示せること |
|---|---|---|
| 仕様のシナリオ | 現在のSpecの受入項目、または合意対象の通常テスト・fixture | 人が確認する期待する振る舞い |
| テストのシナリオ | テスト本体・fixture・実際に到達したassert | テストが何を要求し、どこまで検査したか |
| 実測のシナリオ | 同じ入力で実装を呼び出した観測記録 | その実行で観測できた結果・状態 |

シナリオは派生表示とする。正本を参照し、期待値を独立したファイルへ手で二重管理しない。表示用スナップショットを保持する場合は生成元・内容ハッシュ・仕様ID・観測したrevisionを付ける。編集は元の受入条件へ戻す。保存したスナップショットから正本を自動更新しない。

同じ`artifact_id`、`item_id`、`observed_revision`を引き継ぐ。複数の入力例には表示内のcase IDを付けてもよいが、別の仕様ID体系にしない。合意と実測は異なる情報である。生成成功、再生成功、テスト成功を人間の承認として扱わない。

## 開発前の確認

1. 既存Requirement・Specの対象項目と、利用者、操作対象、前提、入力、期待結果、禁止する副作用を読む。未知の業務判断は未知のまま示す。
2. 通常テストやfixtureがまだない場合は、元のSpecから表示用データを作り、出典と未確認部分を示す。既存fixtureがあれば直接派生させる。実装の出力から期待値を決めない。
3. 期待する場面だけを再生する。実行前の画面には「未実行」を表示し、実測の成功を描かない。
4. 人が前提・操作・結果・境界・拒否時の副作用を確認する。決定は元のSpecの項目・版と表示内容に結び付けて記録する。レビューしたスナップショットのハッシュも残す。
5. 同じ受入条件を使って通常のテストを作る。シナリオデータを実行する独自DSLは必須にしない。`test-first-verification`の既存proof pathに従い、失敗・実装・再検証を進める。

人の確認後に受入条件の意味が変わったら、元のSpecのrevisionと決定記録を更新し、影響する場面を再確認する。現行コードから再生成したスナップショットを、過去に承認された内容として扱わない。

## テストからのレビュー

1. テスト名だけでなく入力、fixture、assert、setup、モックの境界を読む。静的な抽出は候補であり、実行証拠ではない。任意の言語のテストを完全に復元できると主張しない。
2. 対象ランナー用の小さなアダプターで、実行された入力・返り値・状態とassertの期待値・成否を取得する。取得できない値、未到達のassert、未対応の記法は欠落として残す。
3. 合意対象の仕様スナップショット、テストの期待、実測を並べる。前提・入力・対象revisionが同じかを先に確認する。違う場合は一致判定の意味を限定する。
4. 「実測値は一致したがassertがない」「テストの期待が仕様と違う」「拒否したのに状態を変えた」をそれぞれ示す。テスト全体が成功しても、必要なassertの不足を消さない。
5. 人が仕様の意味を確認し、既存レビューの所見へ対象ID・証拠を接続する。差分がない場面の再生だけで仕様全体の正しさを承認しない。未表示の分岐、モック外の連携、E2E、性能等は対応する検証義務へ戻す。

アダプターと観測記録も検査対象である。自己申告の記録や値の一致だけでは、assertがその業務状態を正しく参照したことを証明できない。テスト本体との照合を省略しない。テスト実行には通常の実行権限・副作用境界を適用する。

## 映像にする範囲

- 人的な主体には人物・役割を、数量・状態・移動する情報には対象に合う図形を使う。主体、操作対象、結果を位置と動きで結ぶ。
- 文字は項目名、正確な値、欠落、出典の補足に使う。拒否・未観測・不一致は色だけに依存させない。
- 停止、再生位置の移動、前提・操作・結果へのコマ送りを備える。動きを抑える設定でも意味を保つ。
- 再生時間と業務時間・テストの仮想時計を分ける。カメラ移動や緩急で、未観測の処理順序や因果を作らない。純粋関数は入力と出力だけで十分な場合がある。
- HTML/SVG/Canvas等の決定的な表示を基本とする。生成動画、GIF、MP4は任意の共有媒体であり、仕様や実行証拠の正本にしない。

## 依存なしで動かす例

`references/examples/javascript/`の予約機能は、Node.js 24とブラウザーだけで動く。追加パッケージ、APIキー、外部アカウント、外部通信は不要である。人物と10枠の数量表示で8つの入力例を再生する。各場面の再生は8秒で、処理時間を表さない。

以下は**このスキルのディレクトリを作業ディレクトリとして**実行する。導入先では`.agents/skills/spec-driven-development/`等に読み替える。出力先の親ディレクトリを用意し、未使用のファイル名を指定する。出力は配布対象の`references/`内へ置かない。

```bash
node references/examples/javascript/scenario-review.mjs preview --out /tmp/reservation-preview.html --snapshot /tmp/reservation-spec.json
node references/examples/javascript/scenario-review.mjs review --baseline /tmp/reservation-spec.json --out /tmp/reservation-review.html
```

最初のHTMLを開いて仕様を確認し、次のHTMLでテストの期待と実測を比較する。生成したHTMLは単独でオフライン再生できる。`preview`は予約実装・テストを実行しない。`review`は実際に`node --test reservation.test.mjs`を実行し、失敗した場合も比較HTMLを出力して終了コード1を返す。既存の出力は上書きしない。

| ファイル | 役割 |
|---|---|
| `reservation.cases.mjs` | 通常テストが使う受入fixture。期待値の正本 |
| `reservation.test.mjs` | 通常の`node:test`と`node:assert/strict`による3テスト、8入力例 |
| `scenario-observer.mjs` | 呼び出し前後と`equal`・`deepEqual`を記録する、この例専用のアダプター |
| `scenario-review.mjs` | スナップショット、実行、比較、単独HTMLへの出力 |
| `scenario-player.html` | ブラウザー上の人物・数量・結果の再生 |

この例のassertメッセージ`result`と`reserved`は観測値との対応に使う。未対応のassert、重複した対応、値が結び付かないassertを検査済みとして数えない。最初のassertで失敗した後の項目は未assertとなる。ログの収集は実装の正当性を証明する署名ではない。

サンプルの`accepted`は説明用の固定条件であり、実業務の合意ではない。生成データの`human_review`は常に`not_recorded`とする。人間の承認記録は元のSpecのレビューへ置く。シナリオは単一プロセスの関数呼び出しを扱い、永続化・認可・並行更新・通知を検証しない。

## 採用先への接続と検証

既存の`executable-spec-profile`へ、対象受入項目、正本、ランナー、アダプターの対応範囲、プレビュー・実行・出力コマンド、スナップショットとレビュー記録の保存先を必要な分だけ記す。未実装のアダプターは`unavailable`とする。全テストの移行やCIでの動画生成を必須にしない。

導入前に、正しい例だけでなく次を試す。

- 期待値を誤って変更すると、保持した仕様との不一致が見える。
- assertを削除すると、テスト成功時も検査不足が残る。
- 拒否時に状態を変える実装では、その副作用が見える。
- 入力変更、ランナー失敗、未観測値、参照元の変更を成功と表示しない。
- 生成した表示から、仕様項目・テスト本体・対象実装・実行結果へ戻れる。

この参照と例の配布は、採用先での自動抽出や長期的なレビュー品質の向上を証明しない。任意の言語へのアダプター、業務固有の人物・オブジェクト表現、動画出力は採用先で必要になった範囲だけ追加する。
