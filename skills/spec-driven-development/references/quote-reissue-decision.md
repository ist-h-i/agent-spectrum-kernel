# 通し例：価格改定後に確定見積を再発行する

架空の設計会議を題材にする。以下の業務判断はこの例の前提であり、採用先の承認や実サービスの検証結果ではない。狙いはテストの書き方を見せるだけでなく、テストで区別できる場面が開発の判断をどう変えたかを示すこと。

## 決める前に分かっていたこと

担当者は「見積画面に加えてCSVでも再発行したい」と依頼した。当初案は、二つの出力経路が現在の商品価格から金額を計算するものだった。価格が変わる前なら正しい結果に見える。既存データには見積の参照番号はあるが、過去に確定した金額を裏付ける記録がないものもある。この時点では、値上げ後の再発行で当時の金額と今日の金額のどちらを出すか決まっていない。

| 同じ見積について確かめる場面 | 現在価格でその都度計算 | 確定時の金額を再発行 |
|---|---|---|
| 1,200円で確定し、その直後に表示 | 1,200円 | 1,200円 |
| 商品価格が1,500円になった後に表示・CSV出力 | 1,500円 | 1,200円 |
| 価格改定後に新しい下書きを作成 | 1,500円 | 1,500円 |

二行目を見せて、営業の業務責任者が「確定済みは当時の金額、下書きは現在価格」と決めたものとする。これを要求側の判断とし、版や金額の持ち方は技術側に任せる。テストがこの業務判断を選んだのではない。

## 何を変え、何を変えなかったか

- **責務：** 確定操作がその時点の金額を記録し、画面とCSVは同じ確定記録を読む。現在価格を経路ごとに引く案は、価格改定後の再発行で約束に反するため採らない。商品価格と計算規則の版を保存して再現する案も条件を満たし得るが、必要なのは確定額だけであり、過去の規則を維持する負担が増えるため選ばない。将来、内訳や計算過程の再現まで必要なら方式を見直す。見積を別サービスに切り出す必要はない。
- **着手順：** 帳票の書式を先に増やす計画を改め、先に「確定→価格改定→保存した記録を開き直す→二つの経路で再発行」を確かめる。純粋な金額計算のテストや、二つの出力が互いに一致するだけでは、両方が同じ誤った1,500円を返す場合を除けない。比較の相手は確定時の1,200円とする。
- **公開範囲：** 古い見積に確定額の記録がない場合、「1,500円だった」と推定して出力しない。業務責任者が、履歴を裏付けられる見積だけを再発行対象とすることに同意した場合に限り、その範囲を公開候補にする。同意がない、または新規分も記録が残らないなら、該当する再発行の公開を保留する。現在価格を使う下書きまで止める必要はない。いずれも実際の出荷承認とは別である。

## 後から変える人は何を読むか

仕様 `SPEC-QUOTE-REISSUE` の `AC-CONFIRMED-TOTAL` は二つの利用経路を通して確定額を検証する。`AC-LEGACY-UNAVAILABLE` は根拠のない履歴を確定額として返さない契約、`AC-DRAFT-LIVE-PRICE` は既存の下書きに関する別の契約である。[通常テスト](examples/quote-reissue/quote-reissue.test.mjs)が、初期値・操作・期待結果を示す。実装の選択理由と見直す条件は上記の設計判断に属し、金額の期待値だけを読んでも分からない。採用先では既存の要求・ADR・作業計画にそれぞれ残し、同じ説明を複製しない。

スキルのディレクトリを起点に、Node.js 24の標準機能で確認できる。

```sh
node --test references/examples/quote-reissue/quote-reissue.test.mjs
```

[サンプル実装](examples/quote-reissue/quote-reissue.mjs)を使い、当初案は価格変更後に確定額の契約を満たさず、採用案は一時ファイルを開き直した後の表示・CSVでも契約を満たすことを確かめる。失敗する案を意図的に用意し、その誤りを検出したときに検査が成功する。これはローカルファイルと二つの出力関数に限った実行例であり、実画面、実運用のデータベース、障害時の耐久性、旧データを復元できること、チームやAIの判断能力の向上を証明しない。採用先では実際の保存経路・利用経路で検証してから、その範囲について判断する。
