# 仕様テストの記述規約

## 読めるテストの単位

一つのテストは一つの判断可能な振る舞いを表す。名前を「条件 → 操作 → 観測結果」で読めるようにする。assert数を一つに制限する必要はない。結果と、起こしてはいけない副作用を一緒に検証できる。

機能単位には目的、利用者、用語、責任範囲、参照先だけを置く。各テストには、そのケースを理解するための入力・状態・操作・期待値を置く。隠れたfixtureの既定値に重要な境界条件を埋めない。

| 対象 | 記述すること |
|---|---|
| 正常系 | 代表入力と外部から観測できる結果 |
| 境界 | 等号を含む境界値、その直前・直後の意味あるケース |
| 拒否・エラー | エラーの契約、状態・外部I/Oに残してはいけない変化 |
| 状態遷移 | 開始状態、操作、到達状態、禁止する遷移 |
| 不変条件 | 入力集合や操作列を通じて保つ性質と適用範囲 |
| 連携 | 呼び出し元・呼び出し先が共有する公開契約 |

すべての行をすべての関数へ機械的に追加しない。実際に該当する仕様上の分岐を選ぶ。未決の境界はテスト生成で決めず、必要な判断を質問する。

## 安定した識別と正本

- Specの`artifact_id`と、その中の`item_id`を使う。例は`SPEC-RESERVATION`と`AC-CAPACITY`。クラス名・関数名・ファイル名を仕様IDに埋め込まない。
- 仕様の意味、状態、項目の所属が変わったらSpecの`revision`を上げる。配置変更だけならIDとrevisionを維持する。意味の異なる項目にIDを再利用しない。
- 既存Specに受入条件がある場合はその項目を参照する。テストで新しい正本を作って同じ条件を二重管理しない。新規でテストをSpecの正本にする場合は、テストの名前・入力・assertが受入条件を表す。
- traceを使う参照は`artifact_id`、`item_id`、`observed_revision`を持ち、`docs/lifecycle-traceability-contract.md`に従う。上流依存は既存の`upstream_refs`を使う。
- `status`は`provisional`、`accepted`、`superseded`。これは仕様としての合意状態であり、ASKの証拠強度やテストの実行結果ではない。`accepted`には要求・合意等の根拠を示す。実装から推測した内容を自動で昇格させない。

## 変更に対する寿命

| `lifetime` | 維持する対象 | 変更・削除できる条件 |
|---|---|---|
| `business` | 業務上の観測可能な振る舞い・不変条件 | 根拠のある仕様変更と差分記録 |
| `compatibility` | 公開API、保存形式、イベント等の互換性 | 利用側を含む変更・移行判断 |
| `architecture` | 現在のADRに基づく依存方向や境界 | 対象ADRの変更・置換と適用範囲の再評価 |
| `implementation` | 選択した実装方式の局所的な性質 | 上位の振る舞いを守る別の証拠と変更理由 |

`lifetime`とテストレベルは別である。業務仕様にもユニット・結合・E2Eの証拠があり、アーキテクチャ制約には静的検査があり得る。実装テストへ無理に業務仕様IDを付けない。上位の仕様への関係だけを示してよい。

## 構造と依存

- 業務仕様は安定した公開操作と結果を中心に検証する。privateメソッド、内部の呼び出し順序、DI構成を仕様の期待値にしない。
- 呼び出し回数・順序が外部契約そのものである場合は、その理由を示して検証する。
- clock、乱数、外部I/Oを制御できる境界へ置き、同じ前提から同じ結果を得る。依存性注入のためだけに不要な抽象層を増やさない。
- fakeやmockは外部境界を置き換える。DBの制約、トランザクション、認可、再試行などをfakeだけで保証しない。必要な結合・契約検証を同じ仕様項目へ結ぶ。
- 大きなsnapshotを仕様の正本にしない。snapshotが適切な出力でも、重要な意味と更新理由を人が読める形で示す。
- 性質ベース・モデルベースのテストは、生成範囲、性質、失敗例の再現方法を持つ。実装と同じ計算を期待値側へコピーしない。

## テストを変える前の確認

失敗を見たら、仕様変更、実装の不具合、テスト側の誤り、環境・flakyを切り分ける。greenにするためのassert緩和、skip、削除、snapshot一括更新はしない。

仕様変更では、現在の期待値と新しい期待値、その根拠、影響する利用側を先に確認する。リファクタリングでは業務・互換性の期待値を維持する。設計依存テストを更新する場合も、上位仕様の証拠を失っていないことを確かめる。
