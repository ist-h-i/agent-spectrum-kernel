# 架空の予約機能

これは規約を説明する独立したサンプルであり、実プロジェクトの合意や検証証拠ではない。JavaScript版とPython版は同じ仕様を別々に表す。二つを一つの採用先として索引化しない。

- 目的: 確保済みの数量を更新し、呼び出し元へ結果を返す。
- 利用者: 予約処理を呼び出すアプリケーション。
- `capacity`: 確保できる総数。
- `reserved`: 現在確保している数。
- `quantity`: 今回追加したい数。
- 範囲: 単一プロセス内の判断を例示する。永続化、認可、並行更新、通知は扱わない。
- 前提: `capacity`と`reserved`は非負の整数で、`reserved <= capacity`を満たす。JavaScript版では安全に表現できる整数の範囲を使う。この前提を満たす状態の準備・検証はサンプルの対象外とする。
- 合意状態: サンプルの期待値は説明用に固定しているため`accepted`と記す。実際の業務上の決定を意味しない。

## この予約で、どこまでを単体テストに置くか

この例で呼び出し元に約束するのは「渡された定員と予約済み数に基づいて、指定された数量をすべて確保できるときだけ予約を受け付ける。拒否したら状態を変えない」ことである。結果と更新後の状態の両方を既存の `reserve` 操作で観測できるため、内部の判定関数やその呼出し順序にはテストを置かない。定員・状態も入力なので、無効な数量を増やすだけでなく「定員8、予約済み7、追加2」のように定員を変えて超過時の不変条件を確かめる。適用中の説明用仕様は第2版。仕様IDから正常・境界・拒否のケースを選び、ケースの配列順を仕様の意味にしない。

この判断だけならリポジトリ層、モック、外部サービスは要らない。ただし「別の利用者から同時に受け付けても定員を超えない」ことまで約束するなら判断は変わる。単一プロセスのテストを増やす代わりに、予約を確定する責務と実際の保存・競合境界を決め、そこで確かめるまで同時予約の保証は主張しない。この例がその要件を採用済みという意味ではない。

[JavaScriptの通常テスト](javascript/reservation.test.mjs)と[Pythonの通常テスト](python/test_reservation.py)はそれぞれ独立した見本である。複数経路や旧データで責務・着手順・公開条件が変わる別の例は[確定見積の再発行](../quote-reissue-decision.md)を参照する。
