# テスト戦略から設計・着手順・公開範囲を決める

コードができてから「どこをテストするか」を考える前に、利用者への約束によって設計案の優劣が変わる場面を一つ選ぶ。どの結果を正しいとするか、その結果をどこで確かめられるかを根拠に、状態の責任を持つ機能、先に試す作業、公開してよい範囲を決める。テストを書くこと自体は目的ではない。現在の構造で十分なら変えない。

テスト戦略の策定を依頼された場合、または採用済みプロジェクトで、未決の判断が複数の機能・変更順・公開条件に影響する場合に使う。決まった挙動の局所修正には、通常の仕様・回帰検証で足りる。判断がまだ固まっていなくてもこの検討は始められるが、仮説を合意済みの仕様として実装してはならない。

## 1. コードではなく、案の差が出る場面から始める

- 現在の案と代案がそれぞれ誰に何をもたらすか。最初は同じに見えても、後の価格改定、別の利用経路、保存後の再読込などで結果が分かれるか。実際の要求に関係する違いだけを選ぶ。
- 案で期待結果が異なるなら、それは業務上の選択か、合意済みの約束を満たすための技術選択か。業務判断の出典がなければ、業務責任者にその場面でどちらを求めるかを聞く。それまで両案は仮説であり、片方をテストの正解にしない。技術選択は既存の設計権限の範囲で行う。
- 期待する結果は利用者、既存の契約、確認済みの過去の事実など、候補実装の外から取る。変更前の約束と異なる場合は、その版と決定根拠を残す。実装と期待値を同じ変更で更新しても、合意の証拠にはならない。

## 2. 結果を確かめる境界から、責務と順序を選ぶ

1. どの機能が事実を確定し、誰がそれをいつ利用するかを特定する。案を区別できる最も小さな公開操作と、そこだけでは確認できない条件を選ぶ。既存の窓口で足りるなら、新しい層やサービスは不要。
2. 選択の結果を書く。「この案なら○○をここで読み書きする。別案ではこの条件が崩れる」。両案とも満たすなら、変更・運用・検証の負担が小さい方を選ぶ。外から同じに見えることだけでは、性能・運用費・復旧しやすさの同等性は証明できない。違いが判断を左右する場合だけ対応する測定を加える。
3. 取り消しにくい実装や経路の複製より前に、案を判別できる確認を作業計画に置く。合格なら何を進め、不合格ならどの設計に戻り、未確認ならどの範囲を保留するかを先に決める。無関係な作業まで止めない。
4. データ、運用環境、担当者の判断などが足りなければ、制度上許された範囲で選択肢を示す。例：新規分だけ提供する、先に履歴を調べる、その機能の公開を待つ。対象や約束を狭める判断は業務・公開の責任者に戻す。未実施を失敗と断定せず、テストの成功で公開を承認したことにもしない。

## 3. 約束の寿命と観測場所に応じて残す

| 何を残すか | 正本と検証の場所 | いつ見直すか |
|---|---|---|
| 業務の目的、決定者、以前と違う約束 | 既存の要求・Issueの決定。観測可能な条件は、その約束を担当する機能の公開操作を通す通常テスト、または既存Specの受入項目から参照する | 業務責任者が約束を変えたとき。内部の関数・クラスを変えただけでは期待値を変えない |
| 複数の機能、別の利用経路、保存をまたいで成り立つ約束 | 提供側・利用側の契約や結合テスト。共通計算の単体テストだけで、利用側がそれを使うことまで証明しない | 利用側の契約、保存形式、対象バージョンが変わるとき |
| どの機能が状態を持つか、採用案・却下理由、再検討の条件 | 設計案の比較は既存Issue、重要な継続判断は設計判断記録（ADR）。長く必要な依存方向などに限って検査を添える。理由そのものをテストに翻訳しない | 代替設計へ移るとき。古い方式だけを守る検査は、上位の約束を検証できることを確かめて廃止する |
| 負荷、復旧、実運用、人による合意など | 対応する測定・運用確認・決定記録。何が未確認で公開可否にどう影響するかは既存のリリース判断に残す | 環境・対象範囲・前提が変わったとき。単体テストやモックの成功で代用しない |

仕様IDと版は既存のものを使う。仕様の索引は正本への案内であって承認記録ではない。全部を新しいディレクトリへ移したり、同じ判断を複数の台帳へ転記したりしない。業務・互換性・設計・実装の寿命の区別は[既存の記述規約](spec-writing-conventions.md)、実行するチェックの選び方は[検証範囲の選定](verification-selection.md)に従う。

## 4. 設計・計画・レビューに同じ条件を渡す

段階ごとに別の「完了条件」を考え直さない。後工程は、今回の対象・仕様項目と版・判断の出典を受け取り、その条件に対して何が変わったかだけを加える。

- **要求 → 設計：** 要求には業務責任者が選んだ約束と未決の範囲を残す。設計は、その約束をどの機能が確定し、どの利用側へ渡すかを引き受ける。決裁前の案に accepted のテストを付けない。
- **設計 → 作業計画：** 選んだ責務と、それを覆す結果が出る確認を同じ仕様項目に結ぶ。保存や利用側の検証を先行作業、その根拠を必要とする機能を後続作業にする。下書きなど別の約束は依存させない。
- **検証 → レビュー：** 観測した対象、実行した境界、仕様の版を確認し、該当する検証義務にだけ証拠を結ぶ。別のID・以前の版・未実行のチェックを代用しない。不合格なら設計や作業順を戻す。未実施なら、該当箇所に「判断に必要な証拠がない」と残す。
- **レビュー → 公開判断：** 実装完了と承認・復旧・実環境の根拠を区別する。部分的な成功は部分的な判断にのみ使える。対象を限定するなら、元の要求を黙って弱めず、対象の決定者に戻す。

ASKでは既存のライフサイクル契約の上流参照、仕様・検証義務・証拠の項目IDと版、レビューの証拠不足・リリース判定を使う。参照がつながることは記録の整合であり、業務承認・実行・公開許可の代わりではない。[架空の判断から実行した検証と保留条件までを追う例](examples/quote-reissue/decision-record.md)を参照する。アプリのテストランナーを置き換えず、全案件に追跡データの新設を要求しない。

## 5. 何が決まったら終わりか

重要な判断が一つあれば十分である。元案と異なる場面、誰が何を根拠に決めたか、そのために変えた責務・着手順・公開条件（または変えなくてよい理由）、将来どこを見れば判断し直せるかを、既存の成果物をたどって説明できること。実際の検証結果と、まだやっていない検証は分ける。後からテストや文書を増やしただけなら、設計や進め方に影響した実績とは数えない。網羅率・ケース数の目標、新しい必須帳票・ランナーは設けない。

[確定見積を再発行する通し例](quote-reissue-decision.md)では、同じ金額に見えていた二つの案が、価格改定後に異なる結果を返す。設計・実装順・提供範囲まで追う場合はこちらを参照する。
