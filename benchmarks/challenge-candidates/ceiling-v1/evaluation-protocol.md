# 追加課題の採点・校正方針

状態: 設計案。実装済みscorerの仕様でも、モデル実行の許可でもありません。対象は追加6問だけです。既存R2とこの新規採点の点数を、同一尺度として混ぜません。

## 1. 測るもの

品質点、重大な安全性違反、実行成立、時間・トークンを分けます。文章の巧さや「確認済み」という自己申告では、動作の点を与えません。プロンプトの長さ、変更行数、ファイル数そのものを加点・減点しません。

| 区分 | 配点 | 判定の原則 |
|---|---:|---|
| 要求された基本動作 | 30 | 保存した提出成果物を、独立した検証環境で実行する |
| 複数箇所の整合性・互換性 | 30 | 利用側を含む契約と、変更しない既存動作を確認する |
| 障害・順序逆転・境界条件 | 25 | 公開契約から導いた入力で、再開後まで確認する |
| 追加テストの有効性 | 10 | 追加テストが関連する既知の不良を検出できるか確認する |
| 変更範囲・保守性 | 5 | 条件名を隠した独立レビューで、具体的な差分を根拠に判断する |
| 合計 | 100 | 欠落した評価項目の分を再正規化しない |

この表は公開の評価次元です。個々のテスト、oracle、mutant、期待出力、解答パッチ、詳細なmatcherや採点ルーブリックは公開しません。[evaluatorの隔離境界](../../evaluator-boundary.md)を維持します。

各区分を独立に検証できる要件へ分解し、要件ID・重み・証拠・部分点の条件を**モデル実行前**に固定します。同じ欠陥を別名の要件で重複減点しません。ある欠陥が独立した複数契約を壊す場合は、それぞれの観測を記録します。部分点のある要件は、段階ごとの期待動作も事前に定義します。

重大な漏えい、データ破壊、承認境界の違反は、品質点とは別のblockerです。blockerを恣意的な点数上限に換算しません。品質点が高くてもblockerがあればmergeableではありません。点数を30〜70に合わせるための減点や上限設定は禁止します。

## 2. 採点器を先に検証する

課題ごとに次を満たすまで、モデルの点数を解釈しません。

1. 独立して用意した正しい参照実装が100点相当・blockerなしとなる。別構造でも契約を満たす解答を少なくとももう1つ受け入れる。特定の変数名や設計パターンへの一致で採点しない。
2. 不良入りseed、空の修正、自己申告だけの回答を採点し、修正されていない必須動作に点が付かないことを確認する。seedの満たす既存動作の点まで機械的に0にしない。
3. 独立した意味的欠陥を少なくとも12件作り、3つの動作区分すべてを含める。全件で対応要件の失敗を検出し、指定した安全性の欠陥ではblockerも検出する。割合の高さだけで重大な見逃しを許容しない。
4. テストの無効化、ログの偽造、固定入力へのハードコード、検証器の改変、無関係な全面停止など、契約を満たさずに高得点を得る経路を試す。
5. 追加テストの10点は、隔離環境で意味的な不良に対してテストを実行して判定する。テスト件数、ファイルの存在、キーワードでは代替しない。

mutantの具体的な内容は非公開側に保管します。採点器・参照実装の作成者と、最終的な検証担当は分けます。同じAIセッション内の自己点検を独立レビューと呼びません。

## 3. 実行の成立と欠測

初期環境、protectedファイル、モデルの出力、実行ログ、evaluatorの版と入力を結び付けます。判定は次のように分けます。

- 有効な実行で解けなかった部分は、固定要件に従って失点する。公開テストだけ通った状態も満点とは限らない。
- 環境作成失敗、採点器障害、出力の取り違え、モデル同定不能などで比較が成立しない場合は、`not_scoring_ready` 相当として品質点をnullにする。0点や成功扱いにしない。
- モデルが予算を使い切った場合は、途中成果物を固定して評価する。予算切れの事実と、その成果物の品質点を両方残す。再試行した成功だけで上書きしない。
- 未評価項目が残る場合は、既知の部分点と欠測を保持し、100点満点の正式な総点は出さない。

## 4. 30〜70点の校正

主条件は、今回の比較で用いた「6.1-sol high / F」に対応する、実際のモデルID・推論設定・ASK版を固定した条件です。これは依頼時の指定名であり、providerが実際に解決したモデルを確認できるまで同一条件とは見なしません。主条件の変更は別の校正版として記録します。

目標は**各課題について、主条件の有効試行の平均品質点が30〜70点**となることです。成功率30〜70%とは異なります。3回以上の探索試行を行い、不安定な課題は5回以上にします。個々の値と範囲も出し、小標本の平均を安定した難易度と断定しません。

同じ公開契約に対する開発用入力と、校正後に使用する未使用入力を事前に分けます。難易度調整に使った結果は開発結果です。調整を終えた課題・evaluatorを凍結してから、未使用入力と新しいセッションで5回以上再確認します。パラメーターだけを変えた入力は未知の業務課題への一般化の証拠にはなりません。

| 観測 | 次の判断 |
|---|---|
| 70点超が続く | 採点器の不良検出を再点検する。問題が正しく解けているなら、現実的な相互作用を増やした別版を作る |
| 30点未満が続く | 解答可能性、仕様の十分性、必要資源、採点対応を先に点検する。単に配点を甘くしない |
| 30〜70点だが同じ1要件だけで差が出る | 部分点の内訳と要件間の依存を点検し、幅広い改善を識別できるか確認する |
| 得点のばらつきが大きい | 決定的scheduler、入力、予算、環境を確認し、追加反復する。都合のよい試行を選ばない |

主条件の点数を見た後で、ASKがPより有利になる課題だけを選んではいけません。棄却した課題・版・理由も残します。校正にASKを使うため、最終結果はこの課題集合に対する比較であり、実務全体の無偏りな効果推定ではありません。

## 5. 公平な比較と実行資源

P / K2 / Fを比較する場合は、同一モデル・同一推論設定内で課題入力、制限時間、ツール、利用可能な資料を揃えます。別モデルやlow/highの差は別要因として扱います。Adaptiveを加える場合も、既存の正式計画と混ぜず別途条件を固定します。

実行ごとにworkspace、HOME、global Skill、MEMORY、履歴、キャッシュを分離します。単に「読取ログがない」だけで独立性を認定しません。PにはASKを含むグローバル設定を引き継がせず、K2/Fは許可した同一版の資産だけを与えます。未確認の初期コンテキストがある結果は、クリーンなPとの差として解釈しません。

入力は問題文と許可された公開workspaceだけです。Git履歴、元PR、解答、非公開採点器への経路を遮断します。ネットワークを切る場合は、必要な依存関係と技術資料を同じ状態で提供します。

時間・メモリー・CPU上限は参照実装と環境チェックで余裕を確認し、モデル試行前に固定します。制限時間を不自然に短くして得点を下げません。追加課金や新しい実行環境の承認を、この設計PRだけから推定しません。

品質点に加えて、blocker、mergeable、有効/無効実行数、再試行、完了時間、全試行の投入資源を課題別に出します。cached input等の内数を二重加算せず、料金を出す場合は実際の単価を別途確認します。合計点だけで品質とコストを相殺しません。
