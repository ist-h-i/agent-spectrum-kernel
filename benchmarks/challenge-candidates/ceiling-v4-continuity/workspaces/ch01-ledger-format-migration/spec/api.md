# Public interfaces

`new Ledger(journal)` exports `read(tenant,id)`, `apply(tenant,requestId,changes,expectedHead)`, `migratePage(tenant,limit)`, `activate(tenant)`, `state(tenant)` and `history(tenant,after,limit)`. Calls are synchronous. Valid tenant, row and request IDs match `[A-Za-z0-9_-]{1,40}`. IDs are case-sensitive, scoped to a tenant, and are data rather than object property paths.

A modern value is null (delete) or `{currency:'USD'|'EUR',minor:string}`. Minor is a signed canonical decimal integer with at most 48 digits excluding the sign; no plus sign, leading zero except `0`, or `-0`. Values are exact integers, including beyond IEEE754 safe range. A change is `{id,value}`. One transaction has 1–8 changes, each ID occurring once; order is part of request identity. Additional object fields are ignored. A raw legacy value has the same currency and `amount`, with a canonical signed whole part and exactly two fractional digits. `-0.00` is invalid. Null is deletion in both versions.

`apply` takes a nonnegative safe-integer expected journal head. A successful new request returns `{head:acceptedSequence,duplicate:false}`. A repeat of the same tenant/request ID and same ordered, canonical legacy changes returns the original sequence and `duplicate:true`, even if expectedHead is now stale. A different valid payload for that request throws code `REQUEST_CONFLICT`. With no matching request and a stale head, throw `HEAD_CONFLICT`. Invalid arguments throw `INVALID_INPUT` before request/head inspection. Invalid batches have no durable effects. At a finite competing append, the first call may return its own success, a matching duplicate, or HEAD_CONFLICT. REQUEST_CONFLICT requires an existing same-identity transaction with a different canonical payload. After interruptions stop, retrying an already accepted identical request must return its original sequence with duplicate:true. No call may append an extra transaction or report a receipt for somebody else's request.

`read` returns null for no historical row, otherwise `{id,revision,deleted,value}` with modern value or null. Revision is the sequence of the last transaction affecting that row, including deletion. It describes a journal prefix that existed during the call, never a partial transaction. `history` returns at most limit consecutive raw transactions after the given sequence, in increasing sequence order. Its after is nonnegative safe-integer and limit is 1–32. History remains the legacy format; it is not a second mutable source of truth.

`migratePage` accepts limit 1–32 and returns `{cursor,complete,version}` after a successful durable publication, or `{conflict:true}` after losing a competing publication. It processes at most limit previously unmaterialized transactions. Cursor equals the last fully represented transaction and never skips an unprocessed one; rows are exactly that prefix, with deletion markers retained. Complete is true only if that published cursor equals the head observed at completion. Competing append may therefore make a page incomplete. An already complete page is idempotent in represented contents and preserves an existing activation; a version increment is allowed. Any page that advances cursor invalidates the previous activation, so catching up after a new append requires activation again.

`activate` returns `{activated:boolean}`. True requires an atomic comparison that cursor=head and that the snapshot version/head used for activation have not changed. `state` returns journal metadata plus `ready`, true exactly when a successful activation exists and its cursor still equals current head. An append after activation makes ready false until caught up and activated again. No write is rejected merely because a migration is active. This is a readiness marker, not legacy-writer shutdown.
