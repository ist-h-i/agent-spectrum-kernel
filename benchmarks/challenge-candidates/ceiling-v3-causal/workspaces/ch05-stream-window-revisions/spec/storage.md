# Reconnection and storage

P1 `ingestEnvelope({tenantId,producerId,sequence,events})` is a producer's ordered atomic delivery, not a watermark. IDs are nonempty strings, sequence a positive safe integer, events array<=256. Every normalized event must have the envelope tenant. The producer's first sequence is1; after a successful sequence n the next new sequence is n+1. Gaps return `sequence_gap`, a lower sequence returns `stale_sequence`, both with index:null. A repeat of the latest successful sequence with the same ordered normalized events returns the same `{accepted:true,count}` even after window closure. Same sequence with different normalized events returns `sequence_conflict`. Different producers and tenants have independent sequences. Equivalent legacy/modern events have the same delivery meaning.

P2 Envelope shape/ID/sequence/array violations are `invalid_envelope,index:null`. Invalid event or tenant mismatch is `invalid_event,index:<first index>` and has priority over producer-sequence errors. Sequence decisions have priority over event-state errors for otherwise valid event encodings. For a valid new sequence, event failure priority/order is S4/S5. A rejected envelope has no accepted-state, producer-sequence, output or sink-rejection effects. A successful envelope applies its events atomically and records its receipt. Empty successful envelope advances sequence. At most one outstanding new sequence per producer is assumed; callers may retry any prior delivery, which yields stale_sequence once a later one succeeds. Sequence and revision increments remain safe integers.

P3 `exportCheckpoint()` returns detached JSON `{version:3,windowSize,allowedLateness,watermarks:[[tenant,value],...],events:[<modern event>,...],producers:[{tenantId,producerId,sequence,events:[<modern event>,...],count},...]}`. watermarks contain each known finite watermark once. events contain exactly the currently active latest events including tombstones, no closed history. producers contain exactly the latest successful delivery per known producer; its ordered normalized event body and count are needed for replay identity and remain even when its windows have closed. Entry order is not significant except the events within a producer body. Mutating any exported/ingested checkpoint object later cannot change this pipeline or another pipeline created from it.

P4 Constructor also accepts v1 `{version:1,windowSize,lateness,tenantWatermarks:{tenant:value},rows:[<legacy or modern event>]}` and v2 `{version:2,windowSize,allowedLateness,watermarks,events}`. These forms start without producer receipts. v1 tenantWatermarks must be a non-null non-array object; v2/v3 watermarks are unique valid [tenant,value] pairs. v3 producers is mandatory and must have unique tenant/producer pairs, valid IDs/sequence/events, all body events in that tenant and count equal body length. Unknown versions, wrong configuration, invalid shapes/events, repeated tenant/eventId rows (even if identical), duplicate watermark/producer keys, or conflicting active revisions are rejected with thrown code `invalid_checkpoint` and no sink effects. Closed event rows may be omitted during restoration. The source checkpoint is never mutated. No exported internal objects or arbitrary live subscriptions are part of storage.

P5 `harness/values.mjs:prepare()` initializes the general JSON-operation adapter and returns null. The protected `harness/values.mjs:capture(pipeline,method)` accepts only the public zero-argument JSON methods exportCheckpoint and stats, and returns an opaque jsonValue supporting set(path,value),read(). Paths are bounded JSON property/index paths and cannot access prototypes. This is a general data-operation facility; it gives no extra pipeline behavior or private implementation access.
