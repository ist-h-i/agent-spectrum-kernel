# Protected primitives and bounded schedules

EditServer.request is an atomic compare-and-set on row version. First acceptance consumes operationId+content; the same accepted request is idempotent and changed content is id_conflict. A rejection does not consume the ID. Server rows/receipts/history are authoritative; server versions only increase. load and lookup return detached copies. changesSince(t,row,version) returns fields present in accepted patches after version, even for equal-valued patches. External updates use the same version and field history rules.

EditTransport.send returns a delivery handle, independently indexed per operationId. accept(id,attempt) performs the server request; deliver/duplicate sends the saved result. Omitted attempt means latest. cancel/disconnect suppresses replies, not server effects. A null lookup does not constrain future acceptance of a pending request. Server acceptance, delivery, external notification and disposal can occur in any explicitly scheduled order. No real network is used.

SessionStore.read(key)->{revision,value} and compareAndSwap(key,revision,value)->{accepted,revision} are synchronous primitives; successful CAS atomically replaces one key with a detached value. A missing key is revision0/value:null. Constructor entries may initialize legacy values. observation()->{reads,casCalls,copies,keys} is read-only and cannot reset or alter counters. At most one live writer exists per key; a stale revision is rejected by the store. SESSION_CONFLICT is permitted if an outside writer violates that single-live-owner producer assumption; it is not a substitute for normal recovery progress. Session payloads never contain callbacks, subscriptions or transports.

Valid finite load: <=10 tenants,100 rows/tenant,10 client/session keys,1000 logical edits and1000 delivery steps; all arithmetic remains safe integer. No walltime points. For a trace with M successful mutating API calls, D delivered callbacks and C constructions, each session lineage uses at most 12*(M+D+C+1) CAS calls and the same read bound; checks use protected counters, not candidate statistics. A finite fair sequence that accepts/delivers the remaining operations plus explicit flushes must permit progress. No active-provider abort, real disk/network, cross-process threads or cryptographic collision analysis is required.
