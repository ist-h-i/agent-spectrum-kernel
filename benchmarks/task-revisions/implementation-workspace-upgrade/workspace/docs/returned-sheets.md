# Receiving and disputing field sheets

`import` takes site, id and an ordered array of edits. Each member is `{slot,issue,base,proposal}`. The base is what the field team checked out and the proposal their finished document. Both use the desk document format. Several positions may refer to the same card. Process them in submitted order. Independent sheets, the kiosk and dispatch may be active at the same time. Only business fields travel offline.

Members merge independently. For a scalar field, take the changed value if its peer kept the base, or the shared value if the peers agree. Divergent edits are a conflict. Title, driver, and each retained stop's label and units are independent. Only one peer adding a new stop keeps it. When both add the same ID they must agree on the stop's fields. Removing a base stop is compatible with the other side keeping its fields, even if it moved, or also removing it. Removal against a changed field is a conflict.

The depot's route planner keeps relative ordering, including changes from either peer. Among surviving base stops, a reversal requested by either peer overrides that pair's original order. For a pair involving a new stop, each peer that contains both expresses a precedence. All these precedences must hold together. Contradictory or cyclic routes are disputed. Where independent additions are otherwise unconstrained, take the smallest currently eligible ID first using JavaScript string comparison. Order and array positions matter. JSON object property order does not.

An absent or replaced issue returns retired. If any field, membership or route order conflicts, leave the entire live card untouched. A merged document equal to the live document is unchanged and consumes no revision. Each applied member consumes one revision, current at the time it commits. Never reduce a revision or overwrite unrelated kiosk activity.

`sheet` takes site and id. It returns null if unknown, else `{site,id,items:[{slot,issue,status,version},...]}` in original position order. The same result shape applies to import and `recheck`. An unprocessed member is pending with null version. For applied, record the new version. For unchanged or conflict, record the observed version. Retired takes null. These are durable receipts, including for completed positions beyond a gap. Record the submitted sheet before processing. A reused sheet ID with a different ordered body returns `{"status":"identity_conflict"}` and changes nothing. Replaying the same body, including with reordered object keys, completes pending positions. It preserves all previous receipts. A different site has an independent ID space.

`recheck` takes site and id and revisits disputed positions using their original submissions against the latest live state. It also completes pending positions. It never replays applied, unchanged or retired positions. An unrecognized ID returns null. When more than one position can be processed, visit them in sheet order.

The progress window uses the released `context.progress({site,id,pos})` callback with zero-based pos. Call it once for each newly processed or explicitly rechecked position after recording both its card effect and receipt, before moving to the next position. The callback may block indefinitely, and another process can see the receipt, edit the card, or resume the same sheet during that time. If the first process resumes, it must respect any work that has finished. A crash before receipt cannot expose a card change from that member. On restart callers inspect the ordinary sheet result and submit the original packet again.
