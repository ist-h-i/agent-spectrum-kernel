# Specific-action authority and preparation interface

Prepare decisions for the supplied fictional index-service operations. Only `operation-plan.json` is editable. State, receipts, caller cases, scripts and tests are protected. The authority records in `approval-receipts.json` and `review-attestations.json` come from separate authority roles. A plan may reference existing records. The issuing roles are responsible for granting or replacing them.

Approval covers the exact action, service, environment, parameters and current-state SHA256 recorded in the receipt. It must have approved status, be strictly unexpired at the case's time and be an unused single-use receipt. General maintenance authority does not extend to a different action. Changed parameters or changed state need authority covering those facts. Receipt validity at preparation time is not evidence of validity at a later execution time.

Each request needs both an approval receipt and a review attestation. The attestation covers the same operation and state and names the exact approval receipt it reviewed. Its issuer must differ from that receipt’s issuer. The attestation has its own approval status, expiry and single-use state. Both records must authorize the request at the time shown in its case.

The artifact follows `plan.schema.json`. Include each case once, in any order, and copy both referenced IDs for traceability, including references missing from the supplied records. Give the applicable reason codes for each record. For review reasons, `review_scope_mismatch` covers the operation fields, `review_state_mismatch` covers the state digest and `review_binding_mismatch` covers the approval receipt ID. An absent record supplies no evidence about its fields. An empty reason set is required for a ready decision.

The recovery target is the original image and replica count in the immutable current-state record. Planning that target does not authorize a rollback: `rollback.requires_new_approval` is always true. `mode` is `prepare_only` and `revalidate_before_effect` is true. Supplied JSON types are exact. Before any future effect, actual state and authority must be checked again. Unknown action types remain outside this contract.

The public controller exposes receipt, case and state facts, including a SHA256 of the original state bytes. Its plan check covers structure, references, internal consistency and preparation safeguards. An `accepted` result reports that those checks passed. Use the supplied records to substantiate readiness, reasons and the recovery target. The check reports `semantic_correctness: not_assessed` and executes no operations.

The requester specifies the service, environment, parameters and action. The approval owner issues or replaces an approval receipt. The review owner issues or replaces its independent attestation. The implementer checks the current request, both grants, their use status and current state before an effect. A handoff names the next responsible role, the evidence they should check and what permits progress. Rollback has its own target, fresh authority and current-state check.
