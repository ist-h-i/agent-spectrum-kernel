# Record API error contract
This repository and all scenarios are original fictional examples; no remote service is used.
The record API maps missing_record to status404 and temporary_unavailable to503; every other fault is500. Public codes are the two recognized kinds or internal_error. Known public messages are passed through. Unrecognized diagnostic messages are replaced by 'The request could not be completed'.
Only temporary_unavailable is retryable. When its retryAfterSeconds is a nonnegative integer, response Retry-After must be its decimal string, including zero. No delay header is required when the value is absent or invalid.
The existing client selects missing/conflict/service display labels by status404/409/500+, retries only GET requests with explicit retryable true while below maximumAttempts, waits an available nonnegative integer delay in seconds, and uses1000ms when no usable delay is supplied. Writes are deliberately not retried; the response hint does not override method policy.
The PR changes only response-adapter.mjs. client-policy.mjs is a supplied caller and is unchanged. Review observable behavior across both boundaries. Existing tests check a subset of scenarios; passing those tests alone cannot establish all contract behavior. Run scripts/trace-cases.mjs to obtain before/after observations from the same supplied cases. A finding should identify a changed contract violation and the response required by this document, supported by actual file/line evidence. Preserve correct behavior and avoid expanding the PR.
