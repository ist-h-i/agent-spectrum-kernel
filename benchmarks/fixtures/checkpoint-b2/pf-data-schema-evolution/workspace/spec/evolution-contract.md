# Customer schema evolution
Formalize the legacy optional contactNote extension in v2 as a string or null, with a new default annotation null. Every previously accepted v1 record must remain valid; id/name requirements and extra-property behavior are unchanged. The v2 reader returns a fresh normalized record with contactNote=null when absent, preserving all other values. A schema default is an annotation, not an implicit data rewrite.

Supply the JSON migration plan so missing contactNote values are populated with null, existing notes and all other values are preserved, reruns are idempotent, invalid existing values reject the whole transition without mutating input, and down restores the exact input snapshot. No other field is part of the requested business change.

Plan interface: the fixed interpreter accepts an `up` object with `operation`, `field` and `value`, and a `down` object with `operation` and any operands that operation uses. Supported up operations are `set_field` (assign every record) and `add_if_missing` / `fill_missing` (assign only when absent). Supported down operations are `drop_field` (remove the named field) and `restore_snapshot` / `snapshot_restore` (recover the saved input). These describe the interpreter's available operations; select a plan that satisfies the transition and rollback requirements above.

The fixed local engine supports flat object schemas using type, properties, required, additionalProperties, and string minLength. Property type arrays and unconstrained anyOf type unions (without sibling assertions) are supported; annotations $schema/$id/title/description/default/examples/$comment have no assertion effect. This is a bounded local contract simulator, not a full JSON Schema implementation. Fixed v1/v2 readers and compatibility tests are supplied. Change only schemas/customer-v2.schema.json and migrations/v1-v2.plan.json. Do not change fixed engine/readers/tests/spec, v1 schema, input data or package. No database, deployment or real customer data is involved.
