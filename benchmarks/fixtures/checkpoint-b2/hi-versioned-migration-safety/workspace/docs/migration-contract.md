# Mixed-version migration and rollback truth

Design only a fictional name -> display_name migration. All source records, schemas, matrix and controller are immutable. Complete migration-plan.json; no live database, deployment or external action. V1 reads/writes name only. V2 fallback reads display_name when populated, otherwise name. V2 dual writer updates BOTH names with the same value; v2-only writer updates display_name and cannot preserve a legacy name after contraction.

Expansion keeps name required and adds display_name OPTIONAL while v1 writers remain. Deploy dual writers before backfill or draining old writers. Both backfill and draining legacy writers must complete before a FRESH verification of every display_name matching the latest name. A one-time backfill before old writers stop is insufficient: old writes can invalidate completeness. Only then cut over reads, and only later drop name. Thus rollout_steps contains each exactly once: expand_optional_field, deploy_dual_writer, backfill, drain_legacy_writers, verify_fresh_backfill, cutover_reads, drop_legacy_field. Backfill and drain may occur in either order; all other stated dependencies remain. Plan read_policy is fallback_until_verified and writer_policy is dual_write_until_contract. Execution and any later restore require separately scoped approval and current-state revalidation.

Every rollback case appears once (any order). Set cutover_ready iff legacy_writers=0 and backfill_complete=true. Before contraction, name remains available, so revert_app_keep_expanded is possible without dropping the added field even if backfill is incomplete. This preserves v1 compatibility without reversing data writes. Once name was dropped, backup restore is safe ONLY for the supplied complete snapshot and positively observed ZERO post_snapshot_writes; snapshot_id must be snapshot-before-contract. For a positively observed later write, rollback_possible false, action forward_recover, loss_risk post_snapshot_writes: keep the current v2 data and repair forward. For an unknown write count, rollback_possible null, action manual_review, loss_risk unknown. Never turn absence of write-count evidence into zero or restore a stale snapshot as lossless. Non-restore actions have snapshot_id null. Before-contraction and zero-write restore loss_risk is none.

The public readonly compatibility controller expresses these finite rules and exact JSON types. A plan accepted against fictional snapshots does not prove production compatibility, backup recoverability or absence of an earlier unsafe migration. Unknown application variants, unprovided schema changes and external action histories remain unverified. Only migration-plan.json may change; preserve all existing evidence and tests.
