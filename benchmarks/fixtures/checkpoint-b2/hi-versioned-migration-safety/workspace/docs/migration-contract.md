# Directory compatibility and recovery contract

Plan the fictional `name` to `display_name` migration. Source records, schema capabilities, application behaviors and checkpoint observations are immutable. Only `migration-plan.json` may change. No live database, deployment, restoration or external action is involved.

V1 reads and writes `name` only. The V2 fallback reader uses `display_name` when populated, otherwise `name`; the V2 reader uses `display_name` only. A dual writer updates both fields to the same value. The V2-only writer updates `display_name` and does not preserve a legacy `name`. `schema-phases.json` describes available schema/application configurations, not an execution schedule. The supported operation names in `plan.schema.json` are an unordered vocabulary for the plan you must design.

During overlap, active application versions must retain a compatible field to read and write, and readers must observe the current customer value. Existing rows can have an unpopulated new field. A legacy write can change `name` without changing `display_name`, including after a prior copy. Evidence used to claim migration completeness must account for those writes. A field cannot be required or removed while doing so would break an active application or discard the current value. Read cutover requires complete current values in the new field and no remaining legacy writers. The plan must establish these conditions rather than treating an earlier copy as permanent proof.

Choose a `read_policy` and `writer_policy` from the supported strategies in the schema. Their names describe keeping the legacy field, using fallback or dual behavior during transition, or relying on the new field. Provide the ordered rollout operations with no duplicates and a decision for every supplied rollback case. `cutover_ready` reports whether the checkpoint establishes the read-cutover conditions. `rollback_possible` records true, false or null for supported, disproven or unverified recovery. `action` names the proposed response; `snapshot_id` identifies an existing snapshot only when the response uses it. `loss_risk` records the supported data-loss assessment. These fields must agree with the checkpoint evidence.

Recovery must preserve current committed values. Application reversion depends on the fields and application capabilities still available. Snapshot restoration replaces current data with the snapshot contents: snapshot completeness and writes after capture are therefore material evidence. A null write count is missing evidence, not an observed zero. The supplied complete snapshot is identified in `mixed-state.json`; unprovided backups or recovery mechanisms cannot be claimed verified. A checkpoint with later committed writes needs a response that preserves those values, and a checkpoint lacking write-count evidence cannot support a lossless-restore claim.

`mode` remains `prepare_only`; execution and restoration require separately scoped approval, and current state must be revalidated. The public reader/writer functions demonstrate application behavior. Plan checks cover supported vocabulary, shape, case/snapshot references and these preparation safeguards. They do not supply a rollout order or calculate the recovery decisions. `accepted` means those public checks passed, with `semantic_correctness: not_assessed` and `effect_count: 0`; it is not proof of migration correctness, backup recoverability or absence of earlier unsafe actions.
