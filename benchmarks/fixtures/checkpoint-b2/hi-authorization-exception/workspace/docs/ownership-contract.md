# Fictional ownership and legitimate exceptions

mayAccess(actor,resource,action,exceptions,now) returns a boolean for read/write operations on the supplied ordinary JSON records. An owner may access only if BOTH owner_id and tenant_id match. A service actor may READ system resources within its own tenant; this exception does not permit writes or non-system resources. A support actor may READ an exact resource under a supplied approved exception: actor_id, resource_id, target tenant_id and action must match, and expires_at must be strictly greater than now. The trusted exception array is supplied by the caller in this local model; callers do not manufacture a verified exception from actor.role. A correctly scoped support read can cross the actor's home tenant and is legitimate. Other accesses are denied. A read receipt never authorizes a write.

Report each supplied case whose proposed boolean contradicts the required contract, each once, with the observed before/after booleans, required boolean and severity. Severity is high for an unauthorized grant and medium for a denied legitimate exception. Changed source statement or matching PR diff is the primary locator; caller cases and contract can supplement. Do not flag legitimate owner/service/support exceptions solely because they look privileged. Findings on unspecified actor types, fabricated scopes or nonexistent inputs are outside this closed review and must not be claimed proven.

review.json uses the closed review.schema.json: decision request_changes when the proposed PR has contract violations; findings with case_id, severity, before_allowed, after_allowed, required_allowed, evidence:[{path,line}]; verification state passed requires all three literal commands. Shape validation is not meaning validation. All cases are fictional memory-only authorization outcomes; no real users, permissions, tokens, route handlers, network or production change is involved. Local results do not prove the absence of earlier unauthorized actions.
