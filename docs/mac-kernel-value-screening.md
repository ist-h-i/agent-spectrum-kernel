## Outcome and ownership

Determine whether adding the exact always-on Kernel to an otherwise identical
Mac Codex task produces an engineering improvement worth its extra resources.
Success means a bounded task-class signal worth evaluating further, not universal ASK
superiority, production adoption, or client ROI. Correct refusal at a genuine
human decision boundary is a quality outcome, not a failure to finish.

## What the existing Mac path actually compares

**Verified:** `scripts/ask-local-codex.mjs` builds plain task input versus the
same task with the exact repository `AGENTS.md` prepended (`kernel_only`). It
uses a shared runner, identity/usage validation, sealed local persistence and
offline replay. It is not Adaptive ASK, Full ASK, or a managed Skill portfolio.
Its current fixed JSON P1/P2/P3 scorer is a wiring test; it cannot score arbitrary
engineering findings, executable handoff or human correction effort.

Do not call this two-condition comparison a test of the complete ASK product.
If it shows no benefit, that falsifies only the selected Kernel/task hypothesis;
Adaptive ASK still requires its own exact assets and #198 protocol. No Skills,
C4 context, prompt tuning, request restructuring or model changes may be added
to one arm during this screening.

## Freeze before outputs and authorize separately

The next preparation artifact must bind exact task/input manifests, workspace
revision, evaluator bundle/revision, Kernel bytes, adapter source/tree, native
Node and CLI images, model `gpt-6.1-sol`, reasoning `medium`, effective config,
authentication class, tool/read/write/network boundary, time/token policies,
ordering, repetitions, grading rubric and human review instructions. No model
matrix. Both arms receive identical task facts, files, runtime and constraints;
only Kernel insertion differs. No previous condition output or answers in input.

Use the current time-policy semantics provisionally: startup 120 s, task 120 s
from one valid start receipt, absolute 240 s, bounded drain 2 s, retry 0. Explicit
comparison token policy is 50,000 per trial / 100,000 per pair, checked after each
trial and able to overshoot. A multi-pair budget must be separately frozen and
authorized: these per-pair limits do not authorize an entire experiment. Record
input + output including cached input; do not double-count reasoning. Subscription
usage limits remain external stops, and tokens are not a dollar billing measure.

The current runner orders plain then Kernel and has a fixed JSON task. Before
engineering measurement, minimally support admitted task/workspace/evaluator
binding and reversed condition order; seal the actual order and record each
trial exactly once. Proposed schedule: screening CI plain-first, handoff
Kernel-first, negative plain-first; confirmation repetitions 1/2/3 alternate
order per fixture, with the handoff schedule inverted. A fresh session/workspace
per arm prevents carryover. Fixed order is disclosed, not described as random.
Until this change is implemented and synthetically verified, the proposal is
not executable and no grant should be created.

## Minimal staged comparison

1. Preparation: verify the three existing input/evaluator authorities, fair
   plain solution paths, recoverability, false-positive controls, and grading
   isolation. Reuse existing admission/mutation and #197 scoring contracts.
   Validate synthetic success, failure, unknown usage, cleanup, no retry,
   reversed order, exact inventory and sealed replay. This does not test value.
2. Screening: one pair for each of the three tasks (3 pairs / 6 planned trials),
   only after a fresh exact execution approval. This tests feasibility and
   discriminative headroom, not adoption. Every case remains represented. If
   every positive outcome is at the ceiling, every outcome is at the floor,
   leakage occurs, or a required measurement is unknown, hold this design.
   Revise through a new version and freeze before any successor; do not replace
   just the losing cases. A favorable single pair does not trigger adoption.
3. Confirmation: only after valid screening and separate budget/approval,
   execute the same frozen three tasks for 3 fresh pairs each (9 pairs / 18
   trials), with the predetermined order. Freeze this stage's selection,
   decision rules and order before screening outputs. Screening data is shown
   separately and excluded from the confirmation decision. No extra repeats
   to obtain significance or replace a failed trial.

This is deliberately smaller than #198 and cannot satisfy its 12-fixture pilot,
24-fixture portfolio, four conditions or human sample requirements. It also
cannot satisfy #291 or #285/#286. Repetition supports a local signal, not a
population-level statistical or causal productivity claim.

## Separate measurements and decision rules

Use existing #197 quality/safety judgments in their native dimensions. Preserve
critical missed obligations, valid findings, false positives, scope deviations,
unsupported readiness claims and unauthorized attempted actions separately.
Do not average a serious regression into a favorable overall score.

A human evaluator reviews all outputs in this small subset, using opaque arm
labels and shuffled review order fixed before result access. Remove condition
headers and telemetry from review copies; retained workflow language can make
blinding imperfect, so report this limitation. The reviewer must not construct
or edit the measured inputs/oracles. Freeze obligation/severity mapping and
review instructions before output access; adjudicate ambiguity consistently.

Measure correction/review minutes directly with a timer, concrete required
changes, unresolved decisions and requested rework items. Stop a review at
15 minutes and mark it censored/unresolved; do not count 15 as completion time.
No repair model call is included. Human rework items are observed review burden,
not measured time to implement fixes or deploy. If no human evaluator is
available, these dimensions and the value decision remain insufficient evidence.

Report each arm/repetition, paired differences, median and min/max separately
for quality, critical misses, human effort, tokens and elapsed time. Preserve
startup, post-start and total elapsed where observed. Unknown is never zero;
CLI trial slots are not proof of the number of billable requests. No composite
ROI score and no significance claim from three repetitions.

The following are **proposed screening materiality choices**, to be locked with
the actual input/evaluator freeze before running; they are not #198 or #291
threshold changes, billing limits or measured results:

- **Proceed to a larger task-class evaluation (bounded adopt signal):** on a
  positive task, at least 2 of 3 confirmation pairs prevent at least one critical
  miss, OR directly measured median human correction/review time improves by
  at least 2 minutes with plain median at least 5 minutes. There must be no
  critical quality/safety/scope/false-positive regression on any of the three
  tasks; existing admitted quality dimensions must be non-inferior. On the
  negative task, median extra human review is at most 1 minute and quality is
  non-inferior. Median paired Kernel/plain token ratio must be at most 1.30 and
  total elapsed ratio at most 1.50 per task. Zero/unknown denominators are unknown.
- **Hold:** leakage, ceiling/floor, incomplete/invalid cases, missing/censored
  human effort, uncertain telemetry/identity, inconsistent benefit, or a benefit
  above the provisional overhead limits. These limits express low-complexity
  preference, not universal economics. Any changed threshold requires a new
  protocol before new results; never reinterpret this run to get adoption.
- **Do not adopt Kernel for the tested class:** any confirmed serious regression,
  or complete valid confirmation with no material engineering/human benefit
  while additional resources exceed the limits. Quality ties alone do not prove
  value. A negative-control loss supports bypass for that class, not a claim
  that all ASK is ineffective. For a complete valid quality tie with no material
  human benefit even when overhead is within the limits, retain plain: there is
  no demonstrated reason to add Kernel for that task class. This is absence of
  demonstrated benefit, not proof of universal ineffectiveness. Report
  inconclusive remaining classes separately.

These decisions authorize no production default or Portfolio mutation. Exact
fix implementation time, business ROI, clean-user distribution and the complete
ASK product remain unmeasured.

## Privacy, stop and next implementation boundary

Keep graders, known solutions, prior answers/results and controller source out
of agent-visible task inputs and denied to model tools. Private evidence remains
local with owner-only storage, exact source/identity records, no overwrite and
offline seal verification/reopen. Public issues contain protocol/status only;
propose exact disclosure text for approval before sharing private measurements.

Stop before the next trial on timeout, usage limit or unknown final usage,
identity/input/evaluator drift, permission mismatch, residual-process uncertainty,
leakage or interrupted/unknown execution. Preserve the case; no hidden retry,
substitution, restart under old permission, or result-driven task selection.

Next smallest implementation: one generic task/evaluator binding and reversible
order in the existing core, using one admitted CI evidence fixture as a model-free
integration case. No scheduler, VM, Docker, new scoring authority or evaluation
platform. Then verify all three fixture admissions and the blinded-human-review
availability, seal the full design and budget, and request fresh measured-run
authority. This document creates neither an execution plan nor a grant.
