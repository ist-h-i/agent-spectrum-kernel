# Preparing honest actual-target acceptance inputs

ACCEPT-INPUTS-1@1. Applies to the standalone five-Prompt physical adapter,
not a new evaluator, approval policy, model runner or install permission source.
This document grants no actual-target execution authority. See preinstall-return and bounded
snapshot contracts before any target initialization.

## Permission versus technical/domain inputs

Determine target-use permission from the current request and persistent prior
authorization for the same action/target. A missing technical object is not itself
missing user permission. Do not expand a limited Prompt/management acceptance
scope into app changes, model/native starts, security settings, deploy or unrelated
push. Keep project-specific permission evidence in private operator records.

The adapter consumes an existing approved Portfolio/Evolution decision. Missing
objects/bytes/provenance are **technical input gaps**. Whether a genuine exact
candidate-adoption or rollback decision already exists is a separate domain fact;
verify it for the actual acceptance packet. Do not label every missing
JSON object as missing user permission, or mint self-authenticating authority to
make it pass. Current caller-trusted contexts have provenance outside the CAS;
a hash-valid record alone does not establish that provenance. Existing legitimate
authorization can be represented without repeatedly asking the same question.

## Exact packet to prepare outside target/source

| Item | Required content / verification | What it does not establish |
| --- | --- | --- |
| Source/target envelope | Reviewed implementation HEAD/hash; all exact-head CI; Target root/dev/inode/HEAD/index/full-tree; independent pre-install absence; private preinstall-return record | Model quality or adoption approval |
| CAS root | Canonical private local store separate from source/target; all referenced objects immutable and hash-valid | Trusted organization/operator identity |
| Closed parent/candidate | Registered complete UTF-8 five-file bundles; Asset IDs, versions, records/content/lineage; exact byte diff for human inspection; valid Registry snapshots and caller-trusted Asset contexts | An unregistered local copy is not an Asset |
| Evolution references | receiptObjectDigest, decisionObjectDigest, proposalObjectDigest, candidateObjectDigest, experimentObjectDigest, recommendationObjectDigest | Raw IDs or synthetic samples are not real run results |
| Approved adoption | Existing `verifyEvolutionApplicationReceipt` passes; receipt completed/action adopt_candidate, decision approved, recommendation/proposal/experiment exact; actual trusted human, experiment and evaluation inputs | C1 approved_saved_noop cannot become adoption |
| Parent/candidate selection | Exact selected selection object for each role; proper Asset and parent/result Portfolio lock; trusted Portfolio contexts, applicable high-impact approval grants and verification evidence | Target-use permission is not a Portfolio state transition |
| Independent rollback | Fresh selected rollback whose predecessor is the adoption result lock and exact target is receipt.rollback_anchor; independently trusted `external_portfolio_rollback_authority` | Snapshot bytes/receipt/local plan alone are not rollback authority |
| Per-operation requests | Private0600 single-link request outside source/target, raw digest from trusted caller, live recomputed plan, exact confirmation and authorization for parent/apply/restore; new record for manual preinstall return | Prior confirmation is not a blanket reusable execution token |

Actual key names for the closure are in
`scripts/ask-personal-prompt-adoption-materialization.mjs:closureKeys`:
storeRoot plus the six object-digest references above, and
trustedHumanDecisionAuthorities, trustedExperimentAuthorities,
trustedEvaluationAuthorities, trustedAssetAuthorityContexts,
trustedPortfolioAuthorityContexts, trustedHighImpactApprovalGrants as applicable.
Use the existing verifiers/normal producers; do not copy test-helper trusted
contexts, developer signatures, scores, witnesses or fake authority IDs.

## What can be done without a new model

1. Inventory a supplied genuine packet read-only, checking its scope/source/protocol,
   retained actual results and authority provenance. Reuse eligible existing evidence
   only for its exact subject and limits. A new execution is not required merely
   because physical application is checked on another permitted target.
2. Prepare private request/plan/diff/restore envelopes and actual operator-owned
   decision records through existing producers, if the independent decisions and
   trust roots already exist and cover the exact subjects. Serialization and
   digest calculation add no authority. No speculative user approval is requested
   before those concrete inputs are available for inspection.
3. Run model-free artificial mechanics independently. Label all outputs synthetic,
   fixture-only and not actual-target authority or improvement evidence. This is
   what the new streaming/preinstall drills do.

The current production adapter has **no acceptance-fixture bypass mode**: even
parent bootstrap requires a genuine complete adopt_candidate closure. A temporary
fixture bundle placed in a real project would still cross that boundary if a
synthetic receipt were relabeled as real. Therefore an acceptance-only test bundle
cannot currently be installed through the production adoption path with test-helper
approval. Do not reclassify deterministic file-byte checks as measured model
improvement. A distinct authorized physical-trial contract would be a separate
product design, not something to smuggle into these resource/removal changes.

If no eligible real packet exists, the owner chooses between (a) obtaining a
proper scoped candidate/evidence/decision via existing processes, or (b) explicitly
specifying that separate trial-only product capability. Neither is implemented
or assumed here. A model run is needed only if producing the chosen genuine
experiment's missing evidence actually requires it; no universal model requirement
is inferred. Before any such run, identify exact pinned source/profile/request,
command, output, model/provider, resource bounds and approval boundary, then report
the concrete operation to the parent. We have not prepared or started such a run.

## Operator record

Keep the actual target, current source/CI state, supplied/missing object digests,
private authority provenance, current execution holds, completed actions and
unverified claims in a private operator handoff. Do not copy project metrics or
conversation permission records into the generic product repository. A completed
saved no-op provides no adopt_candidate packet; historical/synthetic evidence
retains its original scope. Missing input elsewhere on a machine is not established
by the absence of a supplied packet. Capacity support and manual absence return
remain independent product mechanics, not actual improvement adoption evidence.
